# Задание 4. Проектирование продажи ОСАГО

## Входные данные

1) Заявка на осаго обрабатывается партнером в 2 этапа
   1) регистрация заявки
   2) получение предложения (не позже чем через 60с)
2) В пике 2500 пользователей
3) готовые предложения должны сразу подгружаться

## Транспорт между core-app и web-приложением

В качестве транспорта между core-app и web-приложением лучше всего выбрать **WebSocket** . Только эта технология сможет выполнить требование мгоновеного отображения предложений и поможет избежать большого числа запросов между веб и core-app.

## Аспекты использования вебсокета 

Соединение открывается между веб приложением и конкретным инстансом core-app. Ответ в вебсокет может отправить только тот же инстанс.

## Взаимодействие между core-app и osago-aggregator

Для формирования предложения по ОСАГО core-app формирует единую заявку, которая должна быть отправлена в партнерские сервисы. 

### Вариант 1. Kafka топик с заявками 
Для независимого поиска предложений от каждого партнера можно использовать Kafka топик с заявками. Для каждого партнера можно реализовать отдельный консьюмер, который бы читал сообщение с заявкой и отправлял ее партнеру.

#### Плюсы
- независимая обработка консьюмерами под каждый партнерский сервис
- минимальная нагрузка на core-app
- сохранение запроса на поиск осаго даже в случае недоступности osago-aggregator
  
#### Минусы
- Заявка скорее всего содержит ПДН, требуется безопасно хранить сообщения в kafka
  
### Вариант 2. REST запрос на регистрацию заявки 
Регистрация заявки в osago-aggregator через REST. Получение запроса должно запустить цепочку запросов в партнерские сервисы. 


#### Плюсы
- Заявка не хранится в кафке
  
#### Минусы
- Нужны ретраи на стороне core-app
- В случае ретрая будут новые запросы ко всем партнерам
- необходимо корректно поддерживать недоступность партнеров

### Вариант 3. REST запрос на регистрацию заявки + сохранение заявки в базу.
Альтернативно можно комбинировать варианты 1 и 2:
посылать заявку через REST, сохранять ее в базе и запускать после этого процесс поиска через команду в kafka. 

#### Плюсы
- Заявка не хранится в кафке
  
#### Минусы
- Сложнее реализация
- Необходимо очищать postgres

### Вывод: Используем вариант 1 с kafka топиком.

## Хранение данных по заявкам в osago-aggregator.

- Заявка должна храниться максимум 1 минуту, пока идет поллинг партенра
- Необходимо сохранять id заявки у партнера, id входящего запроса, host core-app, с которого пришла заявка (для ответа в корректный сокет)
- При поллинге партнеров нужно соблюдать SLA, поэтому необходимо предусмотреть рейт лимит
- При регистрации заявки необходимо предусмотреть retry
- Также можно настроить circuitBreaker, чтобы не нагружать дополнительно партнера

В связи с тем, что данные не требуется хранить дольше 1 минуты, **база данных не требуется**.
**Очередь заявок храним в Redis**

### Процесс обработки в osago-aggregator

1) Получили заявку по kafka
2) каждый консьюмер партнера берет заявку из кафки (можно применять вычитывание батчинг), проверяет, что deadline не наступил и регистрирует ее у партнера
   1) если партнер недоступен или circuit-breaker открыт происходит retry чтения из kafka
3) получив от партнера id заявки происходит сохранение заявки в очередь в редис и коммит оффсета в kafka
4) в каждом инстансе агрегатора есть пул воркеров - процессов, которые забирают из очереди редиса заявку с наибольшим приоритетом, проверяют ее статус и откладывают на некоторое время в случае, если партнер еще не обработал заявку
5) когда поступил ответ от партнера, он отправляется в core-app


### Организация очереди заявок в Redis

- Используем ZSET (sorted set)
- Структура в очереди = request{id, score, deadline, core-app-host}
- Задаем приоритет с помощью времени дедлайна заявки. score = next_poll_at (для новых задач = now())
- Когда воркер берет задачу в работу, он помещает ее в отдельную очередь - active-tasks, проставляет ей ttl (по дедлайну) и выставляет processing_timeout = 5сек. 
- Для взятия задачи в работу используется lua скрипт, который делает peek задач из очереди, и если есть готовая задача, удаляет из очереди и перемещает в active-tasks 
- После того, как воркер проверил статус, если ответ получен, он отправляется в core-app, если не получен, заявка возвращается в очередь с обновленным score (= времени готовности для следующего поллинга). Также происходит удаление заявки из active-tasks
- Если подключается новый под, он смотрит на active-tasks и перемещает в основную очередь задачи, у которых истек processing_timeout (считаем что в этом случае сервис, выполнявший эту заявку упал)

#### Варианты поллинга очереди редиса

1. использование BZPOPMIN. 
Воркер подключается к редису с timeout(0) и висит, пока в очереди не появятся задачи. Как только появляется задача он берет ее в работу и удаляет из очереди.  

Проблема этого метода в том, что как только воркер взял задачу, она удалилась из очереди. То есть если задача окажется отложенной, ее придется возвращать в очередь. Это создаст дополнительную нагрузку на редис. Дополнительный минус  - нет атомарности

2. Поллинг с использованием кастомного sleep у воркеров. 
Проверили задачу, если рано еще брать (score > now()), то воркер засыпает на дельту времени + jitter, не беря в работу задачу. Если задач нет, воркер спит фиксированное время + jitter.

При этом воркер использует lua скрипт с  ZRANGEBYSCORE q -inf now LIMIT 0 N , чтобы проверить есть ли готовые задачки.

Минус в том, что может быть лаг.

**Берем вариант с поллингом и кастомным sleep**

### Отправка ответа в core-app

1. Отправка готового результата в kafka топик. Консьюмер в core-app читает сообщение, видит хост исходного инстанса core-app, откуда поступила заявка и по ресту шлет ему результат.


2. osago-aggregator сам шлет через рест результат в core-app, при этом использует retry.

Этот вариант лучше, так как, если инстанс core-app упал, то веб-сокет разорвался, поэтому нет смысла более надежно хранить результаты в kafka.

**osago-orchestrator сам шлет по ресту ответ в нужный инстанс core-app**
